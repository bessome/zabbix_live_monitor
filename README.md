# Zabbix Live Monitoring

Каркас приложения на FastAPI для мониторинга устройств Zabbix. В нём есть вход, один главный Admin, роли read и read + execute, пять меню устройств (TV_Amplifires, Switches, Modems, VOIP, Routers), поиск, страница устройства, настройки URL API и фильтров по группам или шаблонам, управление пользователями.

`main.py` — точка входа для PyCharm и Uvicorn. Маршруты разделены между `routes_account.py`, `routes_devices.py` и `routes_settings.py`; доступ к Zabbix находится в `zabbix_service.py`, пользователи и настройки SQLite — в `app_storage.py`, общие функции страниц — в `app_web.py`, конфигурация — в `app_config.py`.

## План развития

1. Согласовать версию Zabbix, состав групп/шаблонов и какие именно устройства относятся к каждому меню.
2. Добавить метрики и события на страницу устройства: items, triggers/problems, историю, графики. Уточнить, что считается «онлайн» для каждого типа устройства.
3. Согласовать конкретные операции для read + execute и разрешать их по роли на сервере с журналом действий. Пока эта роль сохранена, но команд выполнения в каркасе нет.
4. Настроить резервное копирование SQLite. Для одного процесса и порядка 40 пользователей текущая схема подходит как старт; при росте нагрузки можно вынести базу и кэш в отдельные сервисы.

Сессия действует максимум 7 дней с момента входа, затем требуется войти снова. После этого обновления пользователям с уже открытой сессией также потребуется повторный вход. Успешные входы, выходы и открытия страниц сохраняются в SQLite. Admin видит журнал через шестерёнку → «Журнал посещений»: 200 записей на страницу, поиск по имени пользователя. Фоновые запросы API для графиков и обновления устройств в журнал не попадают. В базе время хранится как Unix timestamp, а в журнале, отметках «Обновлено» и на графиках отображается по поясу `APP_TIMEZONE` (по умолчанию `Europe/Tallinn`, включая летнее время); смена времени хоста не требуется. Срок хранения настраивается Admin в разделе «Настройки приложения» → «Хранение журнала»; по умолчанию 90 дней. Можно задать от 1 до 3650 дней или 0 для хранения без удаления. При сокращении срока старые записи удаляются сразу, далее очистка выполняется при записи событий и открытии журнала.

## Запуск в PowerShell

Используйте виртуальное окружение проекта и установите зависимости:

    .\.venv\Scripts\python.exe -m pip install -r requirements.txt

Перед первым запуском задайте уникальные секреты и пароль Admin:

    $env:APP_SECRET_KEY = "<случайная строка длиной от 32 символов>"
    $env:ADMIN_PASSWORD = "<пароль Admin длиной от 9 символов>"
    $env:ZABBIX_API_TOKEN = "<API token Zabbix>"
    .\.venv\Scripts\python.exe main.py

## Запуск из PyCharm

В проекте сохранена конфигурация запуска **Zabbix Live Monitoring (local)**. Выберите её справа вверху PyCharm и нажмите **Run** (или **Debug**). Используется интерпретатор проекта `.venv`, скрипт `main.py` и рабочая папка проекта. Откройте http://127.0.0.1:8000.

Локальные параметры читаются из файла `.env` рядом с `main.py`; файл исключён из Git. При подготовке проекта для тестов в нём уже созданы случайные `APP_SECRET_KEY` и `ADMIN_PASSWORD`. Войдите как **Admin**, взяв пароль из `.env`. После первого запуска пароль можно сменить в разделе «Пользователи». Для доступа к реальному Zabbix заполните `ZABBIX_API_TOKEN` в `.env` и укажите URL API в настройках приложения. После изменения `.env` перезапустите Run-конфигурацию.

Если конфигурация не появилась сразу, переоткройте проект в PyCharm или откройте `main.py` и нажмите зелёную стрелку рядом с `if __name__ == "__main__"`.

Откройте http://127.0.0.1:8000. После входа откроется стартовая страница с приветствием; вернуться на неё можно нажатием на название **Zabbix Live Monitoring** в шапке. Разделы устройств доступны через меню. Имя главного пользователя: **Admin**. После первого запуска ADMIN_PASSWORD не требуется: хэш уже хранится в SQLite. APP_SECRET_KEY должен оставаться постоянным между перезапусками, иначе активные сессии завершатся. Для HTTPS установите APP_HTTPS=1; для другого адреса и порта доступны APP_HOST и APP_PORT.

Пароль Admin можно изменить в разделе «Пользователи»; минимальная длина пароля для всех учётных записей — 9 символов. Новым пользователям нужен уникальный email, по которому можно входить вместо имени пользователя. После обновления старой базы администратор задаёт email существующим пользователям и Admin в том же разделе. Для тестов: установите зависимости из requirements-dev.txt и запустите `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`.

В настройках укажите полный URL API, например https://zabbix.example/zabbix/api_jsonrpc.php. Для каждого меню выберите источник (группы хостов или шаблоны), найдите нужные пункты по имени или ID и отметьте их. Можно выбрать несколько. Пустой фильтр даёт пустой список. Списки групп и шаблонов загружаются из Zabbix API и кэшируются на 60 секунд. Используется Zabbix API token в заголовке Authorization. Токен не хранится в базе данных и на странице настроек показывается только его наличие.

Список устройств обновляется каждые 15 секунд. По умолчанию показываются 50 устройств на странице; пользователь может выбрать 25, 100 или 250 и переходить между страницами. Поиск применяется ко всему списку перед пагинацией: пробел, дефис и нижнее подчёркивание в именах считаются одинаковыми разделителями; `ä/a`, `ö/o`, `õ/o` и `ü/u` совпадают в обе стороны. То же соответствие букв действует при поиске групп и шаблонов в настройках. Для устройств текущей страницы одним запросом читается последнее значение item с точным именем `Device description`; оно показано под именем устройства и полностью в его карточке. Если item отсутствует или ещё не имеет значения, отображается «—». Запросы к списку хостов кэшируются на 10 секунд в процессе приложения. Отображаемая доступность берётся из интерфейсов хоста, поэтому она не равна состоянию всех items и triggers.

Интерфейс адаптирован для телефона: меню устройств можно прокручивать горизонтально, а значки выхода и настроек (шестерёнка) находятся в шапке справа. Устройства и пользователи отображаются карточками, разделы фильтров в настройках сворачиваются. Кнопки и поля ввода имеют размер для управления касанием.

Каждый пользователь может выбрать светлую или тёмную тему и сменить свой пароль в разделе «Мои настройки». Для смены пароля нужны текущий пароль, новый длиной от 9 символов и его повторное введение. Admin при создании пользователя и изменении чужого пароля также вводит новый пароль дважды; при редактировании пользователя оба поля можно оставить пустыми, чтобы сохранить прежний пароль. Выбор темы сохраняется отдельно для учётной записи; существующие пользователи после обновления начинают со светлой темы. После изменения файлов интерфейса обновите страницу: адреса CSS и JavaScript содержат версию, чтобы браузер не использовал старый код.

## Пинг на странице устройства

Когда открыта карточка устройства, сервер начинает отправлять по одному ICMP Echo Request в секунду с полезной нагрузкой 128 байт на адрес основного интерфейса хоста в Zabbix. Если интерфейс настроен на DNS, используется DNS-имя. Несколько пользователей одной карточки разделяют один поток проверок. Через 10 секунд без запросов страницы проверка останавливается. На графике показана последняя минута; потери отмечены красным, а текущий RTT, минимум, среднее и максимум обновляются каждую секунду. Значение Windows `time<1ms` отображается как 0.5 мс. Измерения выполняются с сервера приложения (в Docker — из контейнера), поэтому ICMP должен быть разрешён до устройств.

Под графиком легенда `RTT`/`Loss` и аптайм `Uptime`. Аптайм читается напрямую по SNMPv2c из стандартного `sysUpTime.0` (`1.3.6.1.2.1.1.3.0`) через SNMP-интерфейс Zabbix и community соответствующего типа устройства, обновляется каждые 10 секунд. Если SNMP недоступен, показывается `n/a`. По [RFC 3418](https://www.rfc-editor.org/rfc/rfc3418.html) `sysUpTime` измеряет время с последнего запуска SNMP-подсистемы, которое может отличаться от времени работы всей ОС.

Нажатие на надпись или значение «Потери» открывает историю процента потерь из item Zabbix `icmppingloss`. Доступны периоды `1h`, `12h`, `24h`, `2d`, `14d`, как у остальных исторических графиков. Исторические значения Zabbix могут отличаться от текущего процента на минутном графике: проверки выполняются с разных серверов и с разными параметрами ICMP.

## Избранное и история

Каждый пользователь может нажать ☆ в списке или карточке любого доступного устройства. Страница «★ Избранное» в верхнем меню показывает его сохранённые хосты и последние 15 разных открытых устройств. Списки хранятся отдельно для каждого пользователя в SQLite и не зависят от перезапуска приложения; повторное открытие устройства поднимает его в начало истории.

## Каналы модемов через SNMP

Если очередной SNMP-опрос завершился таймаутом или другой ошибкой, вместо последнего значения на карточке показывается `n/a`; после восстановления связи значение обновляется автоматически. Это относится и к каналам модемов, и к `Optical input power` TV_Amplifires.

В карточке Modems справа от более узкого графика пинга показаны значения `Upstream channel US… Level` и `Downstream channel … MHz Level/SNR`; на телефоне блоки располагаются друг под другом. Названия сокращены до `US1 Level`, `DS52 459MHz SNR` и т. п. Для модемов без номера канала поддерживаются `Upstream channel US Level`, `Downstream channel Level` и `Downstream channel SNR` с подписями `US Level`, `DS Level` и `DS SNR`. Подписи US красные, DS Level синие, DS SNR зелёные; SNR ниже 30 мигает красным, US Level выше 52 выделяется красным. Приложение находит соответствующие SNMP item и их OID через Zabbix API, затем каждые 5 секунд опрашивает SNMPv2c непосредственно с сервера приложения до SNMP-интерфейса устройства. Поддерживаются числовые OID, в том числе `get[OID]`, и шаг предварительной обработки Zabbix «Умножение на» (например, `0.1`). Один результат опроса разделяется между пользователями одной карточки.

Если у downstream-канала есть item `Downstream channel N FREQMHz ErrorRate` или `Downstream channel N ErrorRate`, число ошибок в секунду показывается после SNR в скобках. Для одноканального модема также поддерживается `Downstream channel ErrorRate`: он связывается с единственным SNR. Для многоканальных модемов сопоставление идёт по номеру канала, при наличии — по частоте. ErrorRate опрашивается по SNMP раз в 10 секунд; остальные показатели модема — раз в 5 секунд. Если ErrorRate использует шаг предварительной обработки Zabbix «Change per second», приложение вычисляет скорость по двум последовательным SNMP-опросам; до второго опроса отображается `n/a`. При открытии истории SNR значения ErrorRate берутся из истории Zabbix и показываются отдельной линией с правой шкалой за тот же период.

Нажатие на строку канала открывает график истории выбранного item из Zabbix. Доступны периоды `1h`, `12h`, `24h`, `2d` и `14d`; для `14d` используются почасовые средние из trends Zabbix, а при их отсутствии — обычная история. Длинная обычная история сокращается для отображения на телефоне с сохранением минимумов и максимумов. Пока окно открыто, график обновляется каждые 30 секунд для `1h`, раз в минуту для `12h`, раз в две минуты для `24h`/`2d` и раз в пять минут для `14d`.

Если у модема есть включённый числовой item `restarts count per hour`, под каналами показывается компактное последнее значение из Zabbix. Оно обновляется каждые 15 секунд; нажатие открывает график истории этого item с теми же периодами. В конце заголовка модема после имени и IP выводится в скобках сумма рестартов за последние 24 часа: для каждого часового интервала учитывается только последнее значение item, чтобы повторные измерения не увеличивали итог. Суточная сумма кэшируется на минуту; если истории нет, скобки не показываются.

Для каждого типа устройств в настройках есть отдельные поля SNMP read и write community. Если read community не задана, используется `public`; если write community не задана — `private`. Сохранённые значения не выводятся обратно в форму и шифруются в SQLite ключом, полученным из `APP_SECRET_KEY`. При смене `APP_SECRET_KEY` их потребуется задать заново. Write community пока только хранится для будущих действий: приложение не отправляет SNMP SET. Для опроса устройств контейнеру нужен сетевой доступ к UDP-порту SNMP (обычно 161). SNMPv3 пока не настроен.

## Оптическая мощность TV_Amplifires

В карточке TV_Amplifires сначала показан item `Optical input power`, затем график пинга ICMP: на телефоне один под другим, на широком экране слева и справа. OID и шаг предварительной обработки берутся из Zabbix, значение опрашивается напрямую по SNMP каждые 5 секунд с использованием community для этого типа устройств. Значение ниже `−3.3` выделяется красным полужирным. Нажатие на показатель открывает его историю из Zabbix с периодами `1h`, `12h`, `24h`, `2d`, `14d`. Чтобы устройства появились в меню, задайте для `TV_Amplifires` группы или шаблоны в настройках.

## Порты коммутаторов

Плитки уменьшены вдвое и упорядочены по номеру из имени интерфейса, а не по SNMP `ifIndex`. Если SNMP сообщает `ifConnectorPresent` для большинства Ethernet-интерфейсов, показываются только физические разъёмы. При совпадающих номерах у разных физических портов добавляется короткий номер участника/слота, например `1:1` и `2:1`. В настройках приложения Admin может изменить список фрагментов имени интерфейса, которые нужно скрыть. По умолчанию это `Vlan|AUX|Loop`: проверяются `ifName` и `ifDescr` без учёта регистра. Это фрагменты текста, не регулярное выражение; пустое поле отключает фильтр.

В карточке Switches над графиком пинга отображаются физические Ethernet-порты квадратиками. На плитке показан только номер порта; полное имя интерфейса и скорость доступны в подсказке. Серый означает отсутствие линка, оранжевый — активный линк со скоростью ниже 1 Гбит/с (в том числе 100 Мбит/с), зелёный — 1 Гбит/с и выше. При активном линке с неизвестной скоростью порт выделен жёлтым. Состояние берётся напрямую по SNMPv2c каждые 5 секунд; общий кэш не даёт нескольким пользователям опрашивать один коммутатор независимо. Используются стандартные OID [IF-MIB](https://www.rfc-editor.org/rfc/rfc2863): `ifOperStatus`, `ifName`, `ifHighSpeed`, `ifConnectorPresent`, а при отсутствии расширенных значений — `ifDescr`, `ifType`, `ifSpeed`. Некоторые устройства сообщают номинальную, а не согласованную скорость порта; в этом случае цвет соответствует значению, которое отдаёт SNMP-агент.

Нажатие на плитку открывает тест медного кабеля для TP-Link. Admin и пользователи с ролью read + execute могут запустить его; read видит окно без кнопки запуска. Приложение проверяет, что порт выбран из текущего списка, имеет имя вида `1/0/N`, а `sysObjectID` относится к TP-Link. Затем через SNMP write community отправляет SET на `tpPortCableTestFlush.0`, через 5 секунд читает по SNMP read community статусы и расстояния пар A–D из `tpPortCableTestCFEntry`. На одном коммутаторе одновременно допускается один тест. Результат зависит от модели и прошивки: неподдерживаемый MIB вернёт ошибку. Тест может ненадолго отключить линк, в том числе управляющий; это указано в окне перед запуском. [Схема OID и поведения описана TP-Link](https://www.tp-link.com/us/configuration-guides/key_points_of_managing_the_switch_via_snmp/?configurationId=20745).

## Linux и Docker

На Linux установите Docker Engine и Compose. Создайте `.env` из `.env.example`, задайте уникальные `APP_SECRET_KEY` (не менее 32 символов), `ADMIN_PASSWORD` (не менее 9 символов) и `ZABBIX_API_TOKEN`. Убедитесь, что сервер может обращаться к Zabbix API и пинговать адреса устройств. `.env` не копируется в образ.

Для проверки только на самом сервере:

    docker compose up -d --build
    docker compose ps
    docker compose logs -f app

Приложение будет доступно на `http://127.0.0.1:8000` сервера. SQLite хранится в постоянном Docker volume `monitor_data`.

Для доступа с телефона через HTTPS с сертификатом локального центра Caddy укажите в `.env` `APP_DOMAIN=monitor.example.com` или публичный IP-адрес сервера. Если используете имя, направьте его DNS-запись на сервер. Откройте входящие порты 80/443 (для HTTPS нужен 443).

Если сервер выходит в интернет через HTTP-прокси, экспортируйте `http_proxy` и `https_proxy` перед запуском Compose. Они передаются только во время сборки приложения для `apt` и `pip`, а не в работающий контейнер:

    export http_proxy=http://proxy.stv.ee:8888
    export https_proxy=http://proxy.stv.ee:8888

Для загрузки базового Python-образа и образа Caddy прокси нужен также самому Docker daemon. Настройте его отдельно по [инструкции Docker](https://docs.docker.com/engine/daemon/proxy/) и перезапустите службу Docker. Не добавляйте эти переменные в `.env` приложения, если Zabbix API и устройства доступны напрямую через внутреннюю сеть.

Здесь используются два Compose-файла: `compose.yaml` содержит приложение, постоянный том SQLite и локальный HTTP-порт `127.0.0.1:8000`, а `compose.https.yaml` добавляет Caddy на портах 80/443 и включает защищённые cookie. Compose объединяет файлы в порядке аргументов `-f`: второй дополняет первый. Файл с именем `compose.https.yaml` не загружается автоматически, поэтому для HTTPS указывайте оба файла. Без второго запустится только приложение на локальном HTTP-порту. Подробнее — в [документации Docker Compose](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/).

Затем запустите:

    docker compose -f compose.yaml -f compose.https.yaml up -d --build

В `Caddyfile` включены `tls internal` и `default_sni` для доступа по IP: Caddy сам создаёт локальный центр сертификации и сертификат для `APP_DOMAIN`, не обращаясь к публичному CA. На клиентских устройствах установите корневой сертификат Caddy в доверенные, иначе браузер покажет предупреждение. После запуска получите только публичный корневой сертификат (не ключ):

    docker compose -f compose.yaml -f compose.https.yaml cp proxy:/data/caddy/pki/authorities/local/root.crt ./caddy-root.crt

Проверить HTTPS без отключения проверки сертификата можно командой `curl --cacert ./caddy-root.crt https://<APP_DOMAIN>/healthz`. Хранилище `caddy_data` содержит закрытый ключ центра сертификации: не публикуйте его и не удаляйте при обычном обновлении контейнера. Один процесс Uvicorn нужен для общего кэша и общего пинга устройств; не увеличивайте число workers без вынесения этих состояний в отдельный сервис. Проверка `/healthz` доступна Docker healthcheck. Для диагностики ICMP внутри контейнера: `docker compose exec app ping -c 1 -s 128 <адрес_устройства>`.

### HTTPS с собственным wildcard-сертификатом

`compose.cert.yaml` использует `Caddyfile.cert` и два файла из каталога `certs/` в корне проекта. Каталог `certs/` исключён из Git и Docker build context; сертификат и закрытый ключ монтируются в контейнер Caddy только для чтения. Используйте этот Compose-файл вместо `compose.https.yaml`, если уже есть доверенный сертификат. `APP_DOMAIN` в `.env` должен быть DNS-именем, на которое выдан сертификат (например, `monitor.stv.ee` для `*.stv.ee`), и указывать на сервер с контейнерами. Wildcard `*.stv.ee` не подходит для доступа по IP, `stv.ee` или имени вида `a.b.stv.ee`. Проверьте реальные имена и срок действия сертификата:

    openssl x509 -in /root/star_stv_ee_fullchain.crt -noout -subject -ext subjectAltName -dates

На хосте с контейнерами, в каталоге проекта, создайте закрытый каталог и скопируйте файлы **на этот хост** (если исходные файлы на другом сервере, сначала передайте их по защищённому соединению):

    cd ~/zabbix_live_monitor
    install -d -m 700 certs
    install -m 644 /root/star_stv_ee_fullchain.crt certs/star_stv_ee_fullchain.crt
    install -m 600 /root/star_stv_ee.key certs/star_stv_ee.key

В `.env` задайте `APP_DOMAIN=monitor.stv.ee` (замените на своё имя), затем запустите:

    docker compose -f compose.yaml -f compose.cert.yaml up -d --build
    docker compose -f compose.yaml -f compose.cert.yaml ps
    curl -fsS https://monitor.stv.ee/healthz

`star_stv_ee_fullchain.crt` должен содержать сертификат сайта и промежуточные сертификаты; отдельный `star_stv_ee.ca-bundle` тогда не нужен. Ключ `zabbix7_stv_ee.key` относится к другому запросу и не следует использовать вместо `star_stv_ee.key` без проверки соответствия. При обновлении сертификата замените файлы в `certs/` и пересоздайте прокси: `docker compose -f compose.yaml -f compose.cert.yaml up -d --force-recreate proxy`.

Если Caddy сообщает, что ключ не соответствует сертификату, сравните отпечатки открытых ключей (обе команды должны вывести одинаковый SHA-256):

    openssl x509 -in certs/star_stv_ee_fullchain.crt -pubkey -noout | openssl pkey -pubin -outform DER | sha256sum
    openssl pkey -in certs/star_stv_ee.key -pubout -outform DER | sha256sum
